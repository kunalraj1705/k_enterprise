# KRB Enterprise --- Development Documentation

## Implementation Progress --- 19 August 2026

This document records the implementation work completed and verified
today for `k_enterprise`, covering user identity, JWT authentication,
authorization, API error handling, registration security, and
verification.

------------------------------------------------------------------------

## 1. User Identity

The application now maintains both a UUID technical identifier and a
business-level `userId`.

-   **UUID** → internal technical identifier
-   **userId** → business/public identifier

Role-based examples:

``` text
U0000001 → CUSTOMER
A0000001 → ADMIN
E0000001 → OPERATIONS
```

A sequence table maintains independent counters for each user type. The
UUID is retained alongside the generated business `userId`.

------------------------------------------------------------------------

## 2. JWT Subject Changed to `userId`

The JWT subject was changed from the UUID to the business `userId`.

``` java
.subject(user.getUserId())
```

The JWT conceptually contains:

``` json
{
    "sub": "U0000004",
    "email": "customer@krb.com",
    "role": "CUSTOMER"
}
```

Spring Security uses the JWT `sub` claim as the principal name by
default, so:

``` java
authentication.getName()
```

returns:

``` text
U0000004
```

This allows the current authenticated user to be resolved directly from
the `SecurityContext`.

------------------------------------------------------------------------

## 3. Current User Endpoint

The design intentionally does **not** use `/me`.

The base endpoint represents the currently authenticated user:

``` http
GET /api/v1/user
```

The controller obtains the identity from the authenticated principal:

``` java
@GetMapping
public ResponseEntity<UserResponse> getUserMe(Authentication authentication) {
    String userId = authentication.getName();

    return userService.findByUserId(userId)
            .map(user -> ResponseEntity.ok(UserResponse.from(user)))
            .orElseThrow(() -> new ApplicationException(
                    HttpStatus.NOT_FOUND,
                    "User not found: " + userId));
}
```

Flow:

``` text
GET /api/v1/user
        ↓
JWT validation
        ↓
SecurityContext
        ↓
authentication.getName()
        ↓
U0000004
        ↓
findByUserId()
        ↓
User
```

## 5. Generic `ApplicationException`

A generic `ApplicationException` was introduced instead of creating a
separate exception type for every expected application error.

It carries:

-   HTTP status
-   Error message

Example:

``` java
throw new ApplicationException(
        HttpStatus.NOT_FOUND,
        "User not found: " + userId);
```

Another example:

``` java
throw new ApplicationException(
        HttpStatus.CONFLICT,
        "Email already exists.");
```

Authentication and authorization failures remain handled by Spring
Security-specific handlers.

## 7. 401 Authentication Handling

A custom `RestAuthenticationEntryPoint` was implemented for
unauthenticated requests.

Example response:

``` json
{
    "status": 401,
    "error": "Unauthorized",
    "message": "Authentication is required to access this resource."
}
```

The response is generated by Spring Security before the request reaches
the controller.

### Important distinction

``` text
401 → Authentication problem
403 → Authorization problem
```

------------------------------------------------------------------------

## 8. 403 Authorization Handling

A custom `RestAccessDeniedHandler` was implemented for authenticated
users who do not have sufficient authority.

Example response:

``` json
{
    "status": 403,
    "error": "Forbidden",
    "message": "You do not have permission to access this resource."
}
```

This was verified with role-restricted endpoints.

## 9. JWT Role Conversion

The JWT contains a custom `role` claim.

A custom `KrbJwtAuthenticationConverter` converts that claim into Spring
Security authorities:

``` text
CUSTOMER    → ROLE_CUSTOMER
ADMIN       → ROLE_ADMIN
OPERATIONS  → ROLE_OPERATIONS
```

This enables authorization expressions such as:

``` java
hasRole("CUSTOMER")
hasRole("ADMIN")
hasRole("OPERATIONS")
```

------------------------------------------------------------------------

## 10. Method Security

Method-level authorization was enabled using:

``` java
@EnableMethodSecurity
```

This enables annotations such as:

``` java
@PreAuthorize("hasRole('ADMIN')")
```

Authorization is therefore enforced at the method level in addition to
the HTTP security configuration.

------------------------------------------------------------------------

## 11. Resource Server Configuration

The JWT decoder and custom authentication converter are connected to the
OAuth2 resource server:

``` java
.oauth2ResourceServer(oauth2 -> oauth2
        .jwt(jwt -> jwt
                .decoder(jwtDecoder)
                .jwtAuthenticationConverter(jwtAuthenticationConverter))
        .authenticationEntryPoint(authenticationEntryPoint));
```

The JWT decoder validates the token, while the custom converter turns
the JWT role claim into Spring Security authorities.

## 12. Authorization Model

  Operation                             CUSTOMER          ADMIN     OPERATIONS
  ------------------------------ --------------- -------------- --------------
  Current user                      Own identity   Own identity   Own identity
  Business `userId` lookup         Own user only       Any user       Any user
  UUID lookup                                 No            Yes             No
  Privileged user creation                    No            Yes             No
  Public customer registration               Yes            Yes            Yes

The authorization rules are based on actual business responsibility
rather than simply requiring authentication.

------------------------------------------------------------------------

## 13. Ownership Authorization

For:

``` http
GET /api/v1/user/{userId}
```

the authorization rule is:

-   `ADMIN` → any user
-   `OPERATIONS` → any user
-   `CUSTOMER` → only their own `userId`

The implemented rule is conceptually:

``` java
@PreAuthorize(
    "hasAnyRole('ADMIN', 'OPERATIONS') or " +
    "(hasRole('CUSTOMER') and authentication.name == #userId)"
)
```

The rule works because:

``` text
JWT sub
  =
authentication.name
  =
business userId
```

Therefore a customer cannot simply change the path variable to access
another customer's profile.

## 14. UUID Lookup Authorization

The UUID lookup endpoint is currently ADMIN-only:

``` java
@PreAuthorize("hasRole('ADMIN')")
@GetMapping("/id/{uuid}")
```

This endpoint was used to verify the authorization infrastructure.

Verified behavior:

``` text
CUSTOMER → 403 Forbidden
ADMIN    → allowed
```

## 15. Registration Security

A privilege-escalation risk was identified when public registration
accepted a role from the request.

For example, allowing an unauthenticated caller to submit:

``` json
{
    "userRole": "ADMIN"
}
```

would be unsafe.

The design was changed to separate public customer registration from
privileged user creation.

### Public customer registration

``` http
POST /api/v1/user/customer
```

-   Public
-   No authentication required
-   Always creates `CUSTOMER`
-   Role is not selected by the public client

### Administrative user creation

``` http
POST /api/v1/user
```

-   Authentication required
-   `ADMIN` role required
-   Can create the requested role

Supported roles:

``` text
CUSTOMER
ADMIN
OPERATIONS
```

## 17. Security Boundary Verification

The following scenarios were verified:

-   Public customer registration → `201 Created`
-   Unauthenticated privileged user creation → `401 Unauthorized`
-   `CUSTOMER` attempting privileged user creation → `403 Forbidden`
-   `ADMIN` creating a user → `201 Created`
-   `CUSTOMER` requesting their own `userId` → `200 OK`
-   `CUSTOMER` requesting another user's `userId` → `403 Forbidden`
-   `ADMIN` requesting another user's `userId` → `200 OK`
-   `OPERATIONS` requesting another user's `userId` → `200 OK`

The JWT generation, validation, SecurityContext lookup, role conversion,
ownership checks, and error handlers were all verified during
development.

## 19. Security Configuration Boundary

The public HTTP security boundary is now:

``` java
.authorizeHttpRequests(auth -> auth
        .requestMatchers(
                HttpMethod.POST,
                "/api/v1/user/customer",
                "/api/v1/auth/login")
        .permitAll()
        .anyRequest().authenticated())
```

Only login and public customer registration are permitted without
authentication.

The privileged:

``` http
POST /api/v1/user
```

endpoint is protected through:

``` java
@PreAuthorize("hasRole('ADMIN')")
```

This avoids leaving the privileged registration endpoint publicly
accessible.
